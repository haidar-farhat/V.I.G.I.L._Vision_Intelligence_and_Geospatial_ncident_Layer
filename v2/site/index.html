How it works

Everything before the claim reports. The claim has to justify itself.

One Python package in four layers with a strict import direction, a Rust core for the arithmetic that runs per pixel, and one service boundary through which every change to a site passes with a named principal.

What it refuses to claim

A false "armed" is the most expensive mistake this system can make

A relation is inferred, never observed

One camera cannot tell inside from in front of. So every relation carries the overlap, the frames and the distance it was drawn from, and the interface says "probably in the car", never "in the car".

A distance never travels alone

Two positions each known to ±1.4 m are eleven metres apart give or take about two. It is rendered as 11.2 ± 2.4 m on the plan, in the track table, in the incident and in the exported report.

Nothing is a threat by default

The shipped model names knife and scissors; a kitchen raising a critical alert every evening teaches an operator to ignore the word. A site names its own threat labels, and vigil doctor fails when the installed model cannot produce one.

A threshold is measured on this site

Two tracks visible in one frame are different objects by construction. That is ground truth without labels, and it is what the re-identification gate is set from — per scene, live.

Faces and plates are off

Built, behind one switch, off by default, audited, and with no model shipped: every threshold in them is a stated default with no measurement behind it, and each says so in its own docstring.

Nothing needs the Internet

No cloud, no telemetry, no tiles, no updater, no model downloads. An audit fails the build on any address in shipped source, and CI runs the whole suite with outbound traffic dropped at the firewall.

Get it

An installer for each platform, none of them signed

Signing needs a certificate this project does not have. An unsigned installer is honest about what it is; a self-signed one would teach an operator to click through the warning that is supposed to protect them. Each system will warn, and each warning is correct. Verify the download against its SHA256SUMS, install, then run vigil doctor.

Windows unsigned

  • vigil-{{version}}-windows-x64.msiProgram Files, Start menu, PATH
  • …-windows-x64-setup.exethe same, as NSIS
  • …-windows-x64.zipunpack anywhere; needs nothing

Then vigil doctor, or open Vigil from the Start menu for the window.

Linux unsigned

  • vigil-{{version}}-linux-x64.debapt install ./…deb → /opt/vigil, /usr/bin
  • …-linux-x64.tar.gzunpack anywhere; needs nothing

Then vigil doctor. vigil service install writes a systemd user unit and shows it first.

macOS unsigned

  • vigil-{{version}}-macos-arm64.pkg/usr/local/vigil, /usr/local/bin, Vigil.app
  • …-macos-arm64.dmgthe package, on a disk image
  • …-macos-arm64.tar.gzunpack anywhere; needs nothing

Gatekeeper refuses a double-click on an unsigned package: right-click, Open. Then vigil doctor.

Where it stands

Why this page does not say "production ready"

The software is measured; the site it will run at is not. These are the things that stop this being deployable, in the order they pay off, and none of them is a code problem.

1

There is no labelled dataset

The model is an ONNX file the operator supplies, and the shipped one is stock COCO weights that have never seen the site. vigil dataset export writes the corpus and vigil eval scores against corrected labels — and refuses a validation set that shares a day with training. What is missing is the labels, and that needs a person.

2

It has never run on a physical IP camera

Every run so far is a laptop webcam; the longest is ten minutes. RTSP reconnection, packet loss and H.264 corruption are handled in code and exercised by nothing real. The gate that asked for an hour on a real camera before building anything consequential on top was waived, and the decision record says so.

3

The appearance thresholds are provisional

Now measured live per scene rather than fixed, but the only real footage measured is one indoor clip. tools/calibrate.py reads the constants off unlabelled video; it should run on a night from each camera before anything else.

4

Throughput is measured on one integrated GPU

DirectML took detection from 38.5 ms to 4.5 ms here. Nobody has run this on a deployment machine, and the multi-camera claim rests on that number.
